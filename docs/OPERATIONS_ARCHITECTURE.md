## 0. 最重要の前提：Claude Code は「2種類」ある

同じ「Claude Code」という名前でも、動いている場所によってできることが全く違います。
ここを混同すると運用が必ず破綻するため、最初に定義します。

| | **Mac版 Claude Code** | **Web版 Claude Code**（claude.ai/code） |
|---|---|---|
| 動作場所 | NORIZO の MacBook Pro | Anthropic クラウド上の使い捨てLinuxコンテナ |
| 寿命 | 永続 | セッション終了で消滅（中身は全部消える） |
| `~/.ssh` の鍵 | **使える** | 存在しない・持ち込み禁止 |
| SSH（22番ポート） | **使える** | **通信遮断・sshコマンド自体が無い** |
| ConoHa VPS 操作 | **可能** | **不可能** |
| GitHub 操作 | 可能 | 可能（専用トークン） |
| Vercel 操作 | 可能 | 可能（MCP連携） |
| ローカルのプロジェクト実ファイル | 見える | 見えない（GitHubから取得したコピーのみ） |

### この判定の根拠（実測値）

- OS: `Linux vm 6.18.44` / ユーザー: `root` / ホーム: `/root` → macOS ではない
- `~/.ssh/` は**空**。`config` も `known_hosts` も存在しない
- `ssh` / `scp` / `rsync` / `ssh-add` コマンドが**インストールされていない**
- 外向き通信は HTTPS プロキシ経由のみ。生TCPの22番ポートは**到達不可**（実測）
- `gh` CLI も無い（GitHubはMCP連携とトークンで代替）

> **結論：ConoHa VPS への SSH 接続・接続テストは、この Web セッションからは実行できません。**
> PHASE 3〜6 のうち SSH に関わる部分は、**Mac 版 Claude Code で実施する必要があります。**

## 3. 接続方式の比較と決定（PHASE 2）

### 3方式の比較

| 方式 | 適する用途 | 長所 | 短所 | 採否 |
|---|---|---|---|---|
| **A. Mac → ConoHa（直接SSH）** | ログ確認・調査・手動運用 | 最短経路。秘密鍵がMacから出ない。即応性が高い | Macが起動していないと不可 | **✅ 採用（主系）** |
| **B. Mac → GitHub → ConoHa** | コードの反映 | 履歴が残る。差し戻し容易。正本が一元化 | 一手間増える | **✅ 採用（コード反映は必ずこれ）** |
| **C. GitHub Actions → ConoHa** | 自動デプロイ | Macが無くても動く。完全自動化 | GitHub Secretsに**本番サーバーの鍵を預ける**必要がある。設定が複雑 | **⏸ 保留（当面不採用）** |

### 決定した構成

```
コードの流れ：  Mac（修正）→ GitHub（正本）→ ConoHa（git pull で取得）
操作の流れ：    Mac → SSH → ConoHa（ログ確認・再起動・コマンド実行）
```

**なぜ C（GitHub Actions）を今は採用しないのか**

- 現在、本番Webサイトは **すべて Vercel** で動いており、ConoHa VPS は本番配信をしていません。
  → 自動デプロイの必要性がまだ発生していない。
- Actions を使うと、ConoHa へ入れる鍵を GitHub 側に置くことになります。
  秘密情報の保管場所が1つ増え、漏洩時の影響範囲が広がります。
- **必要になった時点で追加すればよく、今入れると管理コストだけが増えます。**

→ 将来 ConoHa 上で常時稼働サービスを動かし始めたら、その時点で C を再検討します。

## 4. Claude Code を ConoHa VPS に入れるべきか

### 結論：**現時点では入れない。**

**理由**

1. **今、入れないと困ることが無い**
   本番Webは全部 Vercel。ConoHa 上で走らせ続けたい長時間ジョブがまだ存在しません。
2. **秘密情報が増える**
   VPS に Claude Code を入れると、Anthropic の認証情報がインターネット公開サーバー上に常駐します。
   Mac に置いておけば、Mac が盗まれない限り漏れません。
3. **Mac版 + SSH で同じことができる**
   「VPSのログを見て」「VPSでビルドして」は、Mac版 Claude Code が SSH 経由で実行できます。
   VPS 側に AI を常駐させなくても目的は達成されます。

### 入れるべきタイミング（将来の判断基準）

以下のどれかが現実になったら、その時に入れます。

- 数時間〜数日かかる処理を、Mac を閉じても回し続けたい
- ConoHa 上で本番サービスが常時稼働し、自動復旧が必要になった
- 複数プロジェクトの定期バッチをサーバー側で回したい

その際も **DEV専用VPSにのみ導入し、本番稼働サーバーには入れない** ことを原則とします。

## 5. SSH 構成（Mac 側で設定する内容）

### 基本方針

- 秘密鍵は **Mac の `~/.ssh/` から一歩も外に出さない**
- 接続先は **IPアドレスではなく別名（エイリアス）** で呼ぶ
  → IPが変わっても設定ファイル1行の修正で済み、IPをチャットや Git に書かずに済む

### `~/.ssh/config` に追加する設定（Mac側）

```
Host conoha-dev
    HostName        <ConoHaのIPアドレス。ここにだけ書く。Gitには絶対に書かない>
    User            <VPSの作業ユーザー名>
    IdentityFile    ~/.ssh/id_ed25519
    IdentitiesOnly  yes
    AddKeysToAgent  yes
    UseKeychain     yes
    ServerAliveInterval 60
```

これにより、以後は `ssh conoha-dev` だけで接続できます。

- `UseKeychain yes` … 鍵のパスフレーズを macOS キーチェーンが覚えるため、毎回の入力が不要
- `AddKeysToAgent yes` … ssh-agent に自動登録。パスフレーズ入力は1日1回程度で済む
- `IdentitiesOnly yes` … 意図しない別の鍵を送信してしまう事故を防止

### 鍵の構成

| 鍵 | 置き場所 | 用途 | 備考 |
|---|---|---|---|
| `id_ed25519`（Mac鍵） | Mac `~/.ssh/` のみ | Mac → ConoHa | ConoHa側の登録名: `NORIZO-MacBook-Pro` |
| ConoHa作成時の旧鍵 | — | 使わない | **動作確認後に ConoHa 管理画面から削除**（要NORIZO承認） |
| Deploy Key（将来） | ConoHa VPS内 | ConoHa → GitHub の `git pull` | **読み取り専用**で作成すること |

## 6. 認証情報の保存場所（どこに何を置くか）

| 情報 | 正しい保管場所 | 絶対にやってはいけない場所 |
|---|---|---|
| SSH秘密鍵 | Mac `~/.ssh/` + macOS キーチェーン | GitHub、チャット、Drive、他サーバー |
| ConoHa APIパスワード | macOS キーチェーン / パスワードマネージャ | リポジトリ、`.env` のコミット |
| ConoHa VPSのIPアドレス | Mac `~/.ssh/config` と ConoHa管理画面 | 公開リポジトリ |
| Vercel / Supabase / Steel のAPIキー | **Vercel の環境変数** | リポジトリ、チャット |
| GitHubアクセス | Mac: `gh auth` または SSH鍵 / Web版: 自動発行トークン | 手動でのトークンコピペ |
| Web版 Claude Code | **何も預けない**（使い捨て環境のため） | 秘密鍵の持ち込み |

### 判断の原則

> **「その情報が漏れたら、何が起きるか」で保管場所を決める。**
> サーバーに入れる鍵は Mac から出さない。Webサービスの鍵はそのサービスの環境変数に置く。

## 7. デプロイルール（全プロジェクト共通・厳守）

```
   ローカルQA
      ↓
   必要な時だけ Preview
      ↓
   NORIZO 確認
      ↓
   Production
```

### Preview を作ってよい条件

NORIZO が以下のいずれかを言った時 **だけ**：

- 「見せて」 / 「確認したい」 / 「プレビュー出して」

**軽微な修正ごとに Preview を作らないこと。** 複数の修正を「確認セット」としてまとめます。

### Production へ反映してよい条件（すべて満たすこと）

1. Preview での確認が完了している
2. `lint` が通っている
3. `typecheck` が通っている
4. `build` が成功している
5. 主要画面のQAが完了している
6. **NORIZO の明示的な承認がある**

→ 1つでも欠けたら本番反映しない。

## 8. 障害時の復旧手順

| 症状 | 対処 | 実行者 |
|---|---|---|
| **本番サイトが壊れた（Vercel）** | Vercel で直前のデプロイに即時ロールバック。原因調査はその後 | Claude Code（Web/Mac どちらでも可） |
| **VPSにSSHで入れない** | ① ConoHa管理画面でVPSが稼働中か確認 ② セキュリティグループで22番が開いているか確認 ③ それでも駄目ならVNCコンソールで復旧 | ChatGPT（ConoHa連携）→ NORIZO |
| **SSH鍵を紛失した** | ConoHa管理画面/VNCコンソールから新しい公開鍵を登録。**Mac側で新規鍵を作り直す** | Mac版 Claude Code + NORIZO |
| **間違ったリポジトリにpushした** | 該当コミットを `revert` で打ち消す（履歴は消さない）。強制pushは禁止 | Claude Code |
| **秘密情報をコミットしてしまった** | ① 直ちに**その鍵/トークンを無効化・再発行**（最優先） ② その後リポジトリから除去。※消しても漏洩済みとして扱う | NORIZO + Claude Code |
| **VPSのディスクが満杯** | ログ・Dockerイメージ・ビルドキャッシュを削除。削除前に必ず内容を確認 | Mac版 Claude Code（要承認） |
| **Webセッションが消えた** | 作業中の内容が未pushなら失われる。**作業は都度pushしておくこと** | — |

## 9. やってはいけない操作（禁止事項）

### 絶対禁止

- 秘密鍵・APIキー・トークンを **GitHub にコミットする**
- 秘密鍵を **Web版 Claude Code（使い捨て環境）に持ち込む**
- 秘密情報を **チャット本文に表示する**
- 共有ブランチへの `git push --force`（履歴の破壊）
- NORIZO の承認なしの **Production 反映**
- 本番データベースへの直接的な破壊操作（`DROP` / 全件 `DELETE` / 無検証マイグレーション）

### 事前報告が必須（実行前に必ず確認を取る）

- ファイル削除・データ削除
- データベース構造の大幅変更
- SSH設定の大幅変更 / 秘密鍵の置き換え
- サーバー再起動・OS再インストール
- ファイアウォール（セキュリティグループ）の変更
- DNS設定の変更
- 課金が発生する操作（VPSプラン変更、ドメイン購入、有料プラン契約）
- 外部サービスへの公開

### 運用上の禁止

- プロジェクトをまたいだ設定の流用（環境変数・DB接続先の使い回し）
- 軽微な修正ごとの Preview 作成
- 原因不明のまま「とりあえず動く回避策」を入れること

## 10. NORIZO が普段使う自然言語の指示例

### どの Claude Code でも使える指示

| 指示 | 起きること |
|---|---|
| 「日本ワイン.jpの本番状態を確認して」 | Vercelの最新デプロイ状況・エラーログを確認して報告 |
| 「この修正をローカルQAして」 | lint / typecheck / build を実行し結果を報告 |
